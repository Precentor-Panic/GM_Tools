# GM_Tools — Phase 18 Design Record (Placeholder): Encounter Guidance

**Status:** design reviewed (§5), not yet task-planned, not yet built. Original placeholder scoped alone; then run through a real review round — a web-research pass on whether "game theory" is even the right lens (it isn't — see §5), two combat/balance-design experts, and two DM personas on opposite ends of how much they care about combat crunch at all. §5 documents what changed as a result and one genuine, unresolved tension the project owner should decide, not something resolved unilaterally here.

**Why this exists, and what it deliberately is NOT:** the goal is guidance, not automated encounter design and not a rules engine. Two upstream product decisions already made, both worth restating so a future reviewer doesn't relitigate them from scratch:
- Official D&D monster-manual content is not redistributable — this tool indexes the SRD (open-licensed) and otherwise expects the DM to bring their own transcribed/pasted content from books they own. No scraping, no bulk import of copyrighted stat blocks.
- Balance math belongs in a deterministic, non-LLM layer (same split as `propagate.mjs`'s existing mechanisms) — an LLM is unreliable at arithmetic/optimization and a DM wants instant, tunable feedback, which only works if it's cheap and deterministic. The LLM's role here is narrow: extraction/derivation at ingestion time, and thematic filtering at suggestion time. It never picks the final combat math.

---

## 1. Two ingestion pipelines, same shape, two different subjects

Both follow `graph-import/writeup-import.mjs`'s established pattern (propose → typed validation errors → preview/dedup → commit), truncation-aware LLM calls via the existing `callModelDetailed` (`mutation-engine/llm-call.mjs`).

**Input mechanism:** no new npm dependency for PDF parsing. Claude's Messages API already accepts PDF documents natively as a content block — send the PDF straight to the API rather than adding a `pdf-parse`-style library and a text-extraction step of our own. This matters specifically for stat blocks, which are often laid out in irregular columns/boxes that a naive text extractor mangles; native document understanding handles that better than scraped text would anyway.

### 1a. Bestiary ingestion (`combat-planning/bestiary.mjs`, new top-level pipeline stage, sibling to `graph-import/`/`time-skip/`)

- Input: pasted text or a PDF page/excerpt containing one or more stat blocks.
- **Revised per §5's review round — split, not one call doing both.** The LLM call extracts ONLY raw structured fields (name, type, CR/level if present, HP, AC, per-attack to-hit/damage dice, multiattack structure, recharge value, legendary action count/cost, lair/aura effects as flags). A separate **pure function** computes the action-economy score and other derived power stats FROM those fields — not LLM judgment. Three independent reviewers converged on this: an LLM silently mis-weighting a recharge-5-6 ability as "always available," or double/under-counting multiattack, would poison a score that a supposedly-deterministic simulator then treats as ground truth. A pure function is testable, versionable, and re-runnable if the formula improves later; an LLM's arithmetic-adjacent judgment isn't any of those things.
- Typed validation error (matching `WriteupImportValidationError`) if the extracted shape doesn't parse.
- **Ingestion-time sanity check, new**: a gross-outlier guard on the derived fields (e.g. DPR-to-HP ratio outside a broad plausible band, attack-bonus-vs-AC implausible relative to stated level/CR) flags the entry for human confirmation before it ever reaches the simulator, rather than trusting one LLM extraction pass into a layer whose whole value proposition is being trustworthy.
- **Show-your-work requirement, new**: the raw extracted fields render alongside the computed score, per entry, not just the collapsed number — a DM needs to be able to eyeball "that ogre's score looks too low" and go fix the extraction, not take a black-box figure on faith.
- **Storage is deliberately NOT the World Fabric graph.** A stat block is mechanical reference data, not narrative fact — same reasoning already applied to Phase 16 (scenes aren't graph entities either). Flat per-\<scope\> JSON store, same `DEFAULT_ROOT`/`GM_TOOLS_*_DIR` convention as `entity-narration.mjs`. Open question for the review round: is a bestiary entry scoped per-world or per-user/library-wide? A monster a DM owns isn't really tied to one campaign, but nothing in this project currently has a library store above the world level — worth a real decision, not an assumption.
- A lighter review step than the graph's mutation-review gate — more like `prep-content-ops.mjs`'s accept/discard pattern than the full pending-mutation batch machinery, since a bestiary entry isn't a graph mutation and routing it through that queue would be the wrong tool.
- Only touches the graph at the point a specific creature becomes a named narrative threat — and even then, by reference (an entity attribute pointing at a bestiary/actor id), never by copying the stat block into graph fields.

### 1b. Party roster ingestion (`combat-planning/party-roster.mjs`, same shape)

- Same input mechanism (pasted text or PDF), same one-call extract+derive pattern, applied to PC character sheets instead of monster stat blocks.
- Extracted/derived fields split into two groups with two different consumers:
  - **Combat-relevant**: class/level, AC, HP, attack bonus/damage-per-round estimate, save DCs, notable defensive/offensive abilities — feeds the heuristic balancer (§2).
  - **Broader build/character-relevant**: skills/expertise, notable traits, backstory hooks — feeds skill-check design and the context-exposure API (§3), not the combat heuristic.
- Stored per-world (unlike the bestiary's open per-user-vs-per-world question, PCs genuinely belong to one campaign) — flat store, same convention.

## 2. Heuristic encounter balancer (`combat-planning/encounter-heuristic.mjs`, pure/deterministic)

- Consumes bestiary entries' derived power stats + the real party roster's derived combat stats — not a generic "4 level-5 PCs" assumption, the actual party. **The review round's clearest priority call: get this part right before investing in simulator sophistication.** A tactical/crunch-focused DM reviewer put it plainly: "I'd take real party + simple average-case math over generic party + gorgeous Monte Carlo simulation" — magic items and multiclass features are exactly what an LLM extraction pass is most likely to fumble, so the show-your-work/sanity-check machinery in §1a matters most here, not in the simulator's own math.
- Replaces CR/XP-budget math (known-weak specifically because it's additive and bolts action economy on as an afterthought multiplier) with an **expected-value round simulator**, revised per §5:
  - **Real termination condition, not a fixed round count.** The original draft simulated forward "a few rounds" — caught as circular by the quant-design review: rounds-to-resolve can't be a fixed input when it's the thing being measured. Simulate until either side's effective HP crosses zero, with a generous cap (15-20 rounds, not 3-4) acting only as a stalemate guard — and if a fight fails to terminate within the cap, surface that explicitly ("does not resolve in the simulated window — check the math") rather than silently reporting a mid-fight snapshot as if it were the outcome.
  - **Burst/recharge effects modeled as an explicit per-round stochastic check inside the simulation loop** (a seeded Bernoulli roll each round, full damage on trigger), not smoothed into a pre-averaged DPR figure. Named by the quant-design review as the single highest-value fix in the whole design: a dragon's breath weapon recharging round 3 and landing on a failed save is a lumpy, time-correlated spike, not a smooth contribution to average damage — averaging it away is the most likely way this tool produces a confidently wrong "balanced" verdict on a fight that's actually a spike-death risk.
  - **Control effects reduce enemy-side effective actions/DPR for N rounds — they are not converted into a damage-equivalent credit on the party's side.** The original "party effective damage/round + control effects vs. enemy HP" framing put hard CC on the wrong side of the ledger; a hold/wall spell doesn't shrink the enemy HP pool, it shrinks the enemy's available actions.
  - **A cheap Monte Carlo pass alongside the EV pass, not instead of it.** Both design-expert reviewers and both DM reviewers converged independently on this: an expected value alone hides tail risk, and "is this fight balanced on average" is the wrong question — a DM wants to know whether it could go badly wrong on bad rolls. N=200-500 seeded-random rollouts reusing the exact same resolution logic as the EV pass (attack-bonus-vs-AC, damage dice, the same burst/recharge Bernoulli checks) is trivial compute and stays instant; report `P(any PC drops to 0)` as a second line under the EV number, not a replacement for it. One reviewer's framing of the actual credibility bar: "an average-case-only tool is basically Kobold Fight Club with extra steps."
  - **A coarse "concentration" knob for same-type packs**, cheap given combatant count is already a first-class lever: for N≥3 broadly-similar enemies, assume a floor fraction of attacks land on the single most-threatened party member rather than spreading independently. Not full focus-fire AI (out of scope, named as a limitation) — just enough to catch the "goblins swarm the wizard" case the per-actor-independent model structurally can't see.
- Needs a "combat system profile" (attack-roll/AC/save math) to run a real simulation — for a monster or PC from a system without a defined profile, degrades to a cruder power-score comparison rather than refusing to function. Bring-your-own-system stays possible, just less precise without a profile.
- Given a target difficulty and a thematically-filtered candidate pool (the LLM's job, next), suggests specific monster combinations/quantities against that target — the "knobs" (add/remove combatants, minion-rules toggle, legendary-action toggle, scaling sliders, the new concentration knob above, and a new **assumed player-tactics slider** — optimal-focus-fire vs. average vs. chaotic-spread, flagged by the tactical-DM review as the single lever they'd reach for most and the design's biggest original gap) all sit on top of this, all still deterministic, all still instant.
- **Presentation discipline, explicit per the quant-design review's framing**: the "false precision" risk in a tool like this is real but is a presentation problem, not a methodology problem. Never show a single confident number with more apparent authority than a CR estimate just because more arithmetic produced it — always pair the EV with the rollout-derived risk percentage and the non-termination flag where relevant.

**LLM's actual job here, deliberately narrow:** given the current scene's context (location, active threat, faction present — pulled straight from the graph, the same grounding pattern `narrate.mjs`'s `buildAdjacencyContext` already uses), suggest which bestiary *tags/types* fit thematically. It narrows the candidate pool by fit; the heuristic picks the actual roster by math. The LLM never decides final difficulty or composition.

## 3. Context-exposure for other LLM tools (`getPartyContext(world)`, in `party-roster.mjs`)

- A compact, prose-ready summary of the party's build-relevant details (skills/expertise, notable traits, backstory hooks — the non-combat half of §1b's extraction), in the same spirit as `buildAdjacencyContext` grounding narration in real graph neighbors.
- Explicitly **opt-in per call site**, not force-injected into every generated response. This operationalizes the stated caution directly: referencing a specific PC's build/trait in generated content is a genuine "feel good" moment for players when it lands naturally and an eye-roll when it's forced into everything. Any prompt template pulling this in should carry explicit guidance to mention a PC detail only when it's naturally, specifically relevant — not as a reflexive callback every time.
- Consumers: the eventual "scene designer helper," skill-check-design generation, and any other future LLM-assisted prep tool that wants to ground itself in who's actually playing — same pattern, opt-in every time, never a default inclusion.

## 4. Explicitly not decided yet — flag for a future pass

- Bestiary scope: per-world vs. per-user/library-wide (§1a).
- Exact shape of the "combat system profile" concept (§2) — how much system-specific math logic this needs, and whether a first version should just hardcode 5e math and treat everything else as the crude fallback.
- Whether encounter instances need any relationship to Phase 16/17's scene concept beyond "can reference a roster + difficulty target" — plausible fit, not designed in detail here.
- UI surface entirely undesigned — this record is engine/architecture only, matching how Phase 16 preceded Phase 17.
- The single-encounter model doesn't account for adventuring-day attrition (multiple fights depleting resources before the "big" one) — a known blind spot CR/XP math has too, inherited here by scope. Worth stating explicitly rather than leaving silently absent; not proposed as something to fix.

## 5. Review round: what changed, and one real tension left for the project owner

**"Game theory expert" was a category error, confirmed by research before assembling reviewers.** Formal game theory (Nash equilibria, adversarial-agent optimization) analyzes strategic interaction between agents with defined competing payoffs — a GM-authored PvE encounter has no such structure; the GM isn't optimizing against the players and monsters don't play optimally. What this design actually needed is **game balance / combat systems design**, a different, TTRPG-relevant discipline (Ian Schreiber's opportunity-cost framing, the Angry GM's tier/slot critique of CR, Matt Colville's action-oriented monsters, Justin Alexander's encounter-distribution argument, Mike Mearls' own on-record admission that the published CR table was a simplified, never-rigorously-validated approximation). The review round was built around that corrected framing: a combat systems designer, a narrower simulation/quant designer to pressure-test the round-simulation math specifically, and two DM personas deliberately chosen for opposite relationships to combat crunch — one tactical/precision-focused, one narrative-first with combat as a rare, minor part of play.

**What changed as a direct result** — all folded into §1a/§2 above: LLM extraction split from score computation (three-way convergence: combat designer, quant designer, tactical DM's "show your work" ask); a real termination condition instead of a fixed round count (caught as a circular-logic bug by the quant designer); burst/recharge modeled as an explicit stochastic per-round check rather than smoothed into average DPR (the quant designer's highest-value single fix); control effects moved to the correct side of the ledger (reducing enemy actions, not crediting party damage); a cheap Monte Carlo rollout added alongside the EV pass for tail-risk reporting (independently converged on by both design experts AND both DM personas — the single most load-bearing finding of the whole round); an ingestion-time outlier sanity check; a concentration/pack knob; a player-tactics-assumption knob.

**The one thing NOT resolved here, on purpose:** the narrative-light DM reviewer pushed back on the core premise itself, not just its implementation — arguing the ingestion/roster layer (having monsters and PC sheets in one searchable place) is genuinely useful, generalizable, low-regret infrastructure they'd use constantly, while the simulator is "crunch-table tooling wearing a system-agnostic coat" they'd never open regardless of how well it's built, and that if anything ships beyond the roster, it should be a single zero-UI "this looks stomp/brutal" sanity flag, not a full simulation subsystem. The other three reviewers engaged with and substantially improved the simulator as specced. This is a genuine fork, not something to average away: **build the full round-simulator (§2) as revised, or ship the ingestion/roster layer as its own useful thing first and treat the simulator as a separate, later, possibly much smaller feature?** Both are coherent, well-argued positions from this review round; picking between them is a product decision for the project owner, not something to resolve by design-record fiat. Whichever way it goes, the narrative-light reviewer's scope-bleed warning stands regardless: no "encounter difficulty" vocabulary should leak into Session Planner or become an assumed dependency of any other feature — this stays its own, opt-in surface.
