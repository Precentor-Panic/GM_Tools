# GM_Tools — Phase 18 Design Record (Placeholder): Encounter Guidance

**Status:** design reviewed twice (§5, §6), not yet task-planned, not yet built. Round 1 (§5) reviewed a full round-by-round simulator and found a genuine fork: build it, or defer it in favor of the ingestion/roster layer alone. The project owner resolved that fork directly — **defer the simulator** (preserved, not deleted, in §7) **in favor of a pure extraction-plus-scoring heuristic**, no simulation of any kind. Round 2 (§6) researched effect-impact taxonomies across systems (Draw Steel, Daggerheart, WoW/LoL crowd-control design) and reviewed the resulting scoring architecture with a game-balance designer. §2 below is the current, resolved v1 design.

**Why this exists, and what it deliberately is NOT:** the goal is guidance, not automated encounter design and not a rules engine. Two upstream product decisions already made, both worth restating so a future reviewer doesn't relitigate them from scratch:
- Official D&D monster-manual content is not redistributable — this tool indexes the SRD (open-licensed) and otherwise expects the DM to bring their own transcribed/pasted content from books they own. No scraping, no bulk import of copyrighted stat blocks.
- Balance math belongs in a deterministic, non-LLM layer (same split as `propagate.mjs`'s existing mechanisms) — an LLM is unreliable at arithmetic/optimization and a DM wants instant, tunable feedback, which only works if it's cheap and deterministic. The LLM's role here is narrow: extraction/derivation at ingestion time, and thematic filtering at suggestion time. It never picks the final combat math.

---

## 1. Two ingestion pipelines, same shape, two different subjects

Both follow `graph-import/writeup-import.mjs`'s established pattern (propose → typed validation errors → preview/dedup → commit), truncation-aware LLM calls via the existing `callModelDetailed` (`mutation-engine/llm-call.mjs`).

**Input mechanism:** no new npm dependency for PDF parsing. Claude's Messages API already accepts PDF documents natively as a content block — send the PDF straight to the API rather than adding a `pdf-parse`-style library and a text-extraction step of our own. This matters specifically for stat blocks, which are often laid out in irregular columns/boxes that a naive text extractor mangles; native document understanding handles that better than scraped text would anyway.

### 1a. Bestiary ingestion (`combat-planning/bestiary.mjs`, new top-level pipeline stage, sibling to `graph-import/`/`time-skip/`)

- Input: pasted text or a PDF page/excerpt containing one or more stat blocks.
- **Revised per §5's review round — split, not one call doing both.** The LLM call extracts ONLY raw structured fields (name, type, CR/level if present, HP, AC, per-attack to-hit/damage dice, multiattack structure, recharge value, legendary action count/cost, lair/aura effects as flags). A separate **pure function** computes the action-economy score and other derived power stats FROM those fields — not LLM judgment. Three independent reviewers converged on this: an LLM silently mis-weighting a recharge-5-6 ability as "always available," or double/under-counting multiattack, would poison a score that a supposedly-deterministic simulator then treats as ground truth. A pure function is testable, versionable, and re-runnable if the formula improves later; an LLM's arithmetic-adjacent judgment isn't any of those things.
- Typed validation error (matching `WriteupImportValidationError`) if the extracted shape doesn't parse.
- **Ingestion-time sanity check, new**: a gross-outlier guard on the derived fields (e.g. DPR-to-HP ratio outside a broad plausible band, attack-bonus-vs-AC implausible relative to stated level/CR) flags the entry for human confirmation before it ever reaches the simulator, rather than trusting one LLM extraction pass into a layer whose whole value proposition is being trustworthy.
- **Show-your-work requirement, new**: the raw extracted fields render alongside the computed score, per entry, not just the collapsed number — a DM needs to be able to eyeball "that ogre's score looks too low" and go fix the extraction, not take a black-box figure on faith.
- **Storage is deliberately NOT the World Fabric graph.** A stat block is mechanical reference data, not narrative fact — same reasoning already applied to Phase 16 (scenes aren't graph entities either). Flat per-\<scope\> JSON store, same `DEFAULT_ROOT`/`GM_TOOLS_*_DIR` convention as `entity-narration.mjs`. Open question for the review round: is a bestiary entry scoped per-world or per-user/library-wide? A monster a DM owns isn't really tied to one campaign, but nothing in this project currently has a library store above the world level — worth a real decision, not an assumption.
- A lighter review step than the graph's mutation-review gate — more like `prep-content-ops.mjs`'s accept/discard pattern than the full pending-mutation batch machinery, since a bestiary entry isn't a graph mutation and routing it through that queue would be the wrong tool.
- Only touches the graph at the point a specific creature becomes a named narrative threat — and even then, by reference (an entity attribute pointing at a bestiary/actor id), never by copying the stat block into graph fields.

### 1b. Party roster ingestion (`combat-planning/party-roster.mjs`, same shape)

- Same input mechanism (pasted text or PDF), same one-call extract+derive pattern, applied to PC character sheets instead of monster stat blocks.
- Extracted/derived fields split into two groups with two different consumers:
  - **Combat-relevant**: class/level, AC, HP, attack bonus/damage-per-round estimate, save DCs, notable defensive/offensive abilities — feeds the heuristic balancer (§2).
  - **Broader build/character-relevant**: skills/expertise, notable traits, backstory hooks — feeds skill-check design and the context-exposure API (§3), not the combat heuristic.
- Stored per-world (unlike the bestiary's open per-user-vs-per-world question, PCs genuinely belong to one campaign) — flat store, same convention.

## 2. Encounter heuristic scorer (`combat-planning/encounter-heuristic.mjs`, pure/deterministic — no simulation)

Resolved per §6: NOT a round-by-round simulator (that design is preserved, deferred, in §7). This is extraction (§1) plus scoring, full stop — no sequencing, no rounds, no Monte Carlo. Priority call, per the review round's clearest, most-repeated finding: **get real-party-ingestion fidelity right before anything else** — a tactical DM reviewer put it plainly: "I'd take real party + simple average-case math over generic party + gorgeous Monte Carlo simulation." Magic items and multiclass features are exactly what an LLM extraction pass is most likely to fumble, so the show-your-work/sanity-check machinery in §1a matters more than any scoring sophistication below it.

- Consumes bestiary entries' derived power stats + the real party roster's derived combat stats — not a generic "4 level-5 PCs" assumption, the actual party.
- **Action economy**: computed from the raw extracted fields (attacks/round, recharge value, legendary action count/cost) by a pure function, not LLM judgment (§1a).
- **Effect-impact taxonomy**, researched across D&D 5e, Draw Steel, Daggerheart, and MOBA/MMO crowd-control design (WoW's Diminishing-Returns categories, League of Legends' hard/soft CC split) — six axes:
  1. Action-economy impact — full turn/action-slot denial (Stun, Draw Steel's Dazed)
  2. Mobility impact — can't move but can still act (Restrained, Root)
  3. Accuracy impact (self) — degrades the target's own effectiveness once they act (Frightened's attack disadvantage, Weakened)
  4. Survivability impact (as target) — makes the target easier to hit/affected (Prone vs. melee, Vulnerable)
  5. Resource-drain impact — guaranteed HP/resource loss over time or on-condition (poison-adjacent, Bleeding)
  6. Forced-action/agency-override impact — compels a specific action rather than blocking one (Charmed, Taunt)
  - A candidate 7th axis (targeting/detection — Hidden/Invisible-type effects) was cut: its threat contribution is almost entirely mediated through axes 1/3 already, not worth its own axis for v1.
  - **Axis 5 is demoted out of the shared "impact" pool** — per the balance-designer review, it's a guaranteed HP delta (damage wearing a status-effect costume), not a probability/availability shift like the other five. Fold it into the existing damage-total math, or report it as its own line — never blended into the same score as axes 1-4/6, which would be adding probabilities to guaranteed damage with no defined exchange rate.
  - **Duration is an axis-aware multiplier on the axis score, not a 7th axis and not a flat multiplier.** Steep/near-linear scaling for axes 1/2/6 (turns denied scales roughly linearly in danger), flatter for axes 3/4 (the marginal terror of a 3rd round of disadvantage drops off), near-1.0/no-op for axis 5 (already priced into the damage sum, and demoted out of this pool anyway).
  - **Aggregation is the actual craft point, more than the axis list itself.** A single effect commonly hits multiple axes at once (a paralysis-equivalent hits both action-economy AND survivability simultaneously) — flat-summing axes for one effect systematically overweights exactly the nastiest effects in the game. Use a dominant-axis-plus-decay function instead: full weight on the highest-scoring axis, a decayed weight (~25-40%) on co-triggered axes, not a flat sum. The balance-designer review named this the single highest-value place to spend design effort — more important than axis count.
- **Burst ceiling**: alongside the expected/average threat score, a separate worst-case number (max recharge-ability damage, a synchronized-crit ceiling) — answers "what if the monsters roll well" without simulating anything. Guard against a "fantasy ceiling": only count burst components a monster can hit unconditionally or with ≤1 free setup step (a Sneak-Attack-style effect needing a prior ally hit doesn't count at full value), or the number becomes unreachable in practice and DMs learn to ignore it.
- **Snowball delta**: the same scoring function run twice — once with the full party, once with a single PC removed — reporting the swing. Run against **two** candidates, not one "most critical" PC: the top damage contributor (matters for burst-race fights) and the top effective-HP/mitigation contributor (matters for attrition fights) — a single "most critical" pick answers the wrong question for half of all encounter types.
- **Asymmetric risk bias, implemented as a secondary flag threshold — never blended into the primary score.** The motivating asymmetry (a DM can cheaply de-escalate a fight going too easy — kill a mob early, phone in a turn — but can't cheaply escalate one going too hard without it feeling arbitrary) is real and worth keeping, but per the balance-designer review: implement it as a threshold on the burst-ceiling number (ceiling exceeds some % of party effective HP → escalate visual urgency), not as a skew baked into the average score. Blending it would make every encounter read as "dangerous" and reintroduce exactly the false-precision/cry-wolf problem that got the full simulator deferred in the first place. Two honest, separately-shown numbers (expected, ceiling) beat one number secretly doing risk-adjustment math nobody can audit.
- **Pack coefficient, resurrected from the deferred simulator's "concentration knob" (§7) because it's genuinely free without simulation**: a one-line static multiplier, `effective_threat × f(mob_count, has_focus_fire_trait)`, where `has_focus_fire_trait` flags things like Pack Tactics or shared-target buffs. Six identical wolves are not six independent threat units summed. Does not attempt actual target-selection AI — that's correctly still out of scope, and no cheap heuristic fixes that particular fidelity gap.
- Needs a "combat system profile" (attack-roll/AC/save math) to compute real scores — for a monster or PC from a system without a defined profile, degrades to a cruder power-score comparison rather than refusing to function. Bring-your-own-system stays possible, just less precise without a profile.
- Given a target difficulty and a thematically-filtered candidate pool (the LLM's job, next), suggests specific monster combinations/quantities against that target — knobs (add/remove combatants, minion-rules toggle, legendary-action toggle, scaling sliders, the pack coefficient above, and an **assumed player-tactics slider** — optimal-focus-fire vs. average vs. chaotic-spread, the tactical-DM review's top-requested lever) all sit on top of this, all deterministic, all instant.

**LLM's actual job here, deliberately narrow:** given the current scene's context (location, active threat, faction present — pulled straight from the graph, the same grounding pattern `narrate.mjs`'s `buildAdjacencyContext` already uses), suggest which bestiary *tags/types* fit thematically. It narrows the candidate pool by fit; the heuristic picks the actual roster by math. The LLM never decides final difficulty or composition.

## 3. Context-exposure for other LLM tools (`getPartyContext(world)`, in `party-roster.mjs`)

- A compact, prose-ready summary of the party's build-relevant details (skills/expertise, notable traits, backstory hooks — the non-combat half of §1b's extraction), in the same spirit as `buildAdjacencyContext` grounding narration in real graph neighbors.
- Explicitly **opt-in per call site**, not force-injected into every generated response. This operationalizes the stated caution directly: referencing a specific PC's build/trait in generated content is a genuine "feel good" moment for players when it lands naturally and an eye-roll when it's forced into everything. Any prompt template pulling this in should carry explicit guidance to mention a PC detail only when it's naturally, specifically relevant — not as a reflexive callback every time.
- Consumers: the eventual "scene designer helper," skill-check-design generation, and any other future LLM-assisted prep tool that wants to ground itself in who's actually playing — same pattern, opt-in every time, never a default inclusion.

## 4. Explicitly not decided yet — flag for a future pass

- Bestiary scope: per-world vs. per-user/library-wide (§1a).
- Exact shape of the "combat system profile" concept (§2) — how much system-specific math logic this needs, and whether a first version should just hardcode 5e math and treat everything else as the crude fallback.
- Whether encounter instances need any relationship to Phase 16/17's scene concept beyond "can reference a roster + difficulty target" — plausible fit, not designed in detail here.
- UI surface entirely undesigned — this record is engine/architecture only, matching how Phase 16 preceded Phase 17.
- The single-encounter model doesn't account for adventuring-day attrition (multiple fights depleting resources before the "big" one) — a known blind spot CR/XP math has too, inherited here by scope. Worth stating explicitly rather than leaving silently absent; not proposed as something to fix.
- The exact naming/numeric scale for the six impact axes (§2) and the dominant-plus-decay aggregation's decay percentage — real implementation-time decisions, not designed to that level of precision here.

## 5. Review round: what changed, and one real tension left for the project owner

**"Game theory expert" was a category error, confirmed by research before assembling reviewers.** Formal game theory (Nash equilibria, adversarial-agent optimization) analyzes strategic interaction between agents with defined competing payoffs — a GM-authored PvE encounter has no such structure; the GM isn't optimizing against the players and monsters don't play optimally. What this design actually needed is **game balance / combat systems design**, a different, TTRPG-relevant discipline (Ian Schreiber's opportunity-cost framing, the Angry GM's tier/slot critique of CR, Matt Colville's action-oriented monsters, Justin Alexander's encounter-distribution argument, Mike Mearls' own on-record admission that the published CR table was a simplified, never-rigorously-validated approximation). The review round was built around that corrected framing: a combat systems designer, a narrower simulation/quant designer to pressure-test the round-simulation math specifically, and two DM personas deliberately chosen for opposite relationships to combat crunch — one tactical/precision-focused, one narrative-first with combat as a rare, minor part of play.

**What changed as a direct result** — all folded into §1a/§2 above: LLM extraction split from score computation (three-way convergence: combat designer, quant designer, tactical DM's "show your work" ask); a real termination condition instead of a fixed round count (caught as a circular-logic bug by the quant designer); burst/recharge modeled as an explicit stochastic per-round check rather than smoothed into average DPR (the quant designer's highest-value single fix); control effects moved to the correct side of the ledger (reducing enemy actions, not crediting party damage); a cheap Monte Carlo rollout added alongside the EV pass for tail-risk reporting (independently converged on by both design experts AND both DM personas — the single most load-bearing finding of the whole round); an ingestion-time outlier sanity check; a concentration/pack knob; a player-tactics-assumption knob.

**The fork this round left open, resolved by the project owner directly (see §6):** the narrative-light DM reviewer pushed back on the core premise itself, not just its implementation — arguing the ingestion/roster layer is genuinely useful, generalizable, low-regret infrastructure, while a full round-simulator is "crunch-table tooling wearing a system-agnostic coat" regardless of build quality. The project owner agreed with that instinct, for an additional, independent reason: a hand-built simulator sits in an awkward middle tier — more machinery than a scoring heuristic needs, nowhere near the fidelity (position, focus-fire, tactical AI, bonus-action economy) that a real fight-outcome model would need to be trustworthy, and that fidelity gap is exactly what this project's separate RL-training work exists to close at a completely different tier of investment. **Decision: defer the full simulator (preserved in §7), replace it with a pure extraction-plus-scoring heuristic (§2, revised in §6).** The narrative-light reviewer's scope-bleed warning stands regardless of which path was chosen: no "encounter difficulty" vocabulary leaks into Session Planner or becomes an assumed dependency of any other feature.

## 6. Review round 2: the scoring-heuristic reframe

After deferring the simulator, the project owner proposed the concrete replacement: action-economy scoring plus a general, cross-system taxonomy for status-effect/condition "impact" (so the same scoring works beyond D&D 5e), explicitly asking for research grounding before finalizing the axis list, plus a game-balance-designer review of the result.

**Research findings** (full digest not reproduced here, see conversation record): **Draw Steel** (MCDM/Colville) is the closest existing worked example — Malice (a GM-side action-economy currency), Villain Actions (Colville's "Action Oriented Monsters" homebrew, now codified core rules), and a small closed condition list where each condition maps to one specific mechanical lever (Dazed = action-slot denial, Weakened = accuracy debuff, Bleeding = resource-drain-on-action). **Daggerheart**'s conditions are thinner and cleaner (Hidden, Vulnerable, Restrained) but its action economy isn't a per-actor budget at all (spotlight-based), so it informed the condition taxonomy but not the action-economy scoring. The richest precedent by far: **World of Warcraft's Diminishing Returns system** — a real, shipped, developer-authored taxonomy of exactly this kind (Stuns/Roots/Incapacitates/Disorients/Silences/AoE Knockbacks), built explicitly for balance/fairness, more mature than anything TTRPG design discourse has produced on its own. League of Legends' hard-CC/soft-CC split and its explicit "forced-action" category (Taunt/Charm/Berserk) rounded out the taxonomy — Schreiber's *Game Balance* itself yielded nothing beyond the opportunity-cost framing already found in round 1.

**The balance-designer review's verdict, folded into §2 above**: six axes is the right count, but the real craft is in aggregation (dominant-axis-plus-decay, not flat summing) more than the axis list itself; axis 5 (resource-drain) doesn't belong in the same pool as the other five since it's guaranteed damage, not a probability shift; duration should be an axis-aware multiplier, not its own axis; both burst ceiling and snowball delta are good, cheap, correct proxies and should ship, with two guardrails (burst ceiling needs an unconditional-or-cheap-setup guard against fantasy numbers; snowball delta needs two candidate PCs, not one); the asymmetric-risk bias belongs on a secondary flag threshold, never blended into the primary score, to avoid quietly reintroducing the false-precision problem that got the simulator deferred; and the pack-coefficient concentration knob is cheap enough to pull forward from the deferred simulator design even without any simulation.

## 7. Deferred: full round-by-round simulator (preserved design, not being built now)

This is the round-1-reviewed simulator design, superseded in v1 scope by §2's scoring heuristic per §6's resolution — kept here rather than deleted because it represents real, independently-reviewed work, and because it may be worth revisiting later (the RL-training project this codebase already has a separate track for is the natural "if we ever want real fight-outcome fidelity" path, at a completely different tier of investment than either this or a hand-built simulator).

- Would have replaced CR/XP-budget math with an **expected-value round simulator**: party effective damage/round vs. total enemy HP, enemy effective damage/round vs. party effective HP, simulated to a real termination condition (either side's effective HP crosses zero, not a fixed round count — caught as circular by the quant-design reviewer, since rounds-to-resolve can't be a fixed input when it's the thing being measured), with a generous round cap only as a stalemate guard.
- Burst/recharge effects would have been modeled as an explicit per-round stochastic check inside the simulation loop (a seeded Bernoulli roll each round, full damage on trigger), not smoothed into average DPR — named as the single highest-value fix to the simulator design, since averaging away a lumpy, time-correlated spike (a dragon's breath landing round 3) is the most likely way a smoothed model produces a confidently wrong "balanced" verdict on a fight that's actually a spike-death risk.
- Control effects would have reduced enemy-side effective actions/DPR for N rounds, not converted into a damage-equivalent credit on the party's side.
- A cheap Monte Carlo pass (N=200-500 seeded rollouts reusing the EV pass's own resolution logic) would have run alongside the EV pass, reporting `P(any PC drops to 0)` rather than an average alone — the round's most load-bearing finding, independently converged on by all four round-1 reviewers, and effectively superseded by §2's burst-ceiling/snowball-delta pair as a non-simulated way to get similar risk signal.
- Needs a "combat system profile" (attack-roll/AC/save math) to run — for a system without a defined profile, would have degraded to a cruder power-score comparison.
