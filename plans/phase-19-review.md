# GM_Tools — Phase 19 Design Record: Encounter Builder UI

**Status:** design confirmed, not yet task-planned or built. This is the frontend for Phase 18's engine (`plans/phase-18-review.md`/`plans/phase-18-tasks.md`) — no new server routes needed, `/api/combat-planning/*` already exists and is exercised by tests. Grounded in a real multi-round focus group: a research pass on existing tools (Kobold Fight Club, D&D Beyond's Encounter Builder, Foundry's PF2e/Draw Steel encounter modules, cross-system tools), four DM personas reacting twice (open-ended, then reacting to a concrete proposal), and two independent UX designers proposing and then refining a design against both. No mention of maps, terrain, or positioning occurred anywhere across any round — the process was deliberately kept from priming that topic, and the signal never emerged organically, so no pivot to a maps/battle-map system is warranted from this round.

---

## 1. The confirmed shape

**Entry point — one screen, two ways in, not a fork.** The screen opens on a difficulty rail (Easy/Medium/Hard/Deadly as large, primary, click targets — never a bare numeric slider), with a small click-to-edit numeric chip next to whichever tier is active for anyone who wants precision. Clicking a tier immediately calls `suggestEncounter` against the current checked-in roster and renders 2-3 suggested combinations — there is no separate "Generate" button and no monster-browsing step required first. This single flow serves both ends of the DM spectrum the review round surfaced: it's simultaneously the "declare intent before touching a stat block" flow a precision-focused DM wants and the "one click to a usable answer" gut-check a minimal-prep DM wants — the same action means both things to both people.

**Roster/attendance — a client-side filter over a persisted pool, not a rebuilt roster.** Every ingested party member (`listPartyMembers(world)`) renders as a checkbox chip, checked by default. Unchecking removes that member from the array passed into `suggestEncounter`/`computeSnowballDelta` — a two-click swap. This is a pure UI-layer concept; `party-roster-store.mjs` needed no schema change to serve both a stable, always-fully-checked table and a West-Marches-style table where attendance changes mid-evening. Each chip carries an HP-freshness indicator (see §2) and a "Resync from Foundry" button re-reads current actor HP into the working session's data — explicit, not a silent background sync, matching this project's established no-silent-write discipline.

**Score band — one dominant figure, everything else visibly secondary but never hidden.** `expectedScore` renders as a bar/tier label (Plain mode: just the tier word, large; Precise mode: adds the number and all four tier thresholds simultaneously, per D&D Beyond's "show tier and number together" precedent rather than KFC's single-marker bar). A **Plain/Precise toggle**, styled like the existing List/Graph toggle convention, defaults to Plain for everyone and persists per-browser (`localStorage`, matching `graph-view.js`'s cached-state convention) — this default was chosen specifically because a narrative-light DM's warning ("if it leads with numbers I'll bounce") applies to anyone's first look at the tool, not just that persona.

Two things are **permanent, mode-independent fixtures**, never gated behind the Plain/Precise toggle:
- The **snowball-delta callout** — a two-line/two-pill row, one per `computeSnowballDelta`'s two real candidates (top damage contributor, top effective-HP contributor). Plain: "risky if Elena drops" (shown only when the delta crosses a threshold, suppressed otherwise). Precise: the percentage for both candidates, unconditionally. This is permanent because it was independently named, across personas, as the actual reason anyone would open this tool at all — it answers a question DMs consistently said they can't do in their head.
- The **burst-ceiling indicator** — a quiet corner badge in both modes, never a headline number. Per round-3 refinement, this badge should be **visually absent, not merely subtle**, on any catalog entry that's never been run through the difficulty tooling — presence itself is a signal, not just its prominence.
- **Attendance staleness line** — whenever checked attendance differs from the full roster, a literal sentence renders under the score band: "as of tonight's roster: Elena, Finn, Priya (3/5 present)." Suppressed at full attendance, so a stable table never sees it.
- **HP staleness** — per round-3 refinement, the "synced Nm ago" indicator on each roster chip must be more than a small gray label a DM's eye slides past — it color-shifts (gray → amber) past a staleness threshold, not relying on the DM to read and interpret a timestamp mid-prep.

**Two disclosures, deliberately different, not one compromise.** An **"Adjust ▸"** panel holds every editable knob (`minionRules`, `legendaryActions`, scaling, pack coefficient, player-tactics slider) — closed by default, and per round-3 refinement, its trigger must not *invite* the click: no "3 more options available"-style nudge copy implying the suggestion is provisional. If the suggestion looks done, there should be no visual reason to open it. Separately, a **"Why this score? ▸"** disclosure is read-only — per-combatant threat contribution, which multiplier actually fired — answering "why does it think that" without making anything more tinkerable from that surface. These stay two different affordances because they answer two different DM needs (transparency vs. control) that the review round found don't actually conflict once separated.

**Catalog — present the whole time, secondary until touched.** Below/beside the suggestion, the full accepted bestiary is browsable: left-side facets (creature type, CR-band — not exact CR, environment/region tag), a **System selector** that reveals/hides system-specific facets rather than trying to force every system's fields into one shared filter rail, and a compact **six-axis "impact fingerprint" glyph** per row (a small spoke icon, not a full readout) usable as its own filter/sort axis — e.g. "heavy on mobility-denial" — since the six-axis taxonomy is genuinely portable across systems in a way CR never was. Add mechanic is **click, not drag** (this tool has no spatial canvas to justify drag's overhead, unlike the Foundry modules the research surveyed): a `+Add` per row on repeat click creates individually-tracked combatants; once a row exists in the working roster, a `+/−` stepper appears for a shared-count group, mirroring D&D Beyond's individual-vs-mob fork. An optional theme text box above the facets (e.g. "undead crypt") wires into `proposeThematicTags` to narrow the candidate pool before `suggestEncounter` runs — left blank (the default), the suggestion path never touches an LLM call at all.

**Score-confidence encoded in the number's own shape, not a badge alone.** A full-profile creature/PC shows a solid decimal (e.g. `14.2`); a crude-fallback estimate (no defined combat-system profile) shows a banded range in a visually distinct dashed/outlined treatment (e.g. `Moderate (10–16 est.)`), never a decimal. Truly unscoreable content (`{scored:false}` from the engine — an unrecognized effect, or a homebrew entry with nothing quantitative at all) occupies the identical layout slot with a flat "Unscored — reference only" pill — same position, same size, never an omitted or collapsed card, so its absence-of-precision reads as intentional rather than broken. Per round-3 refinement, a fuzzy/banded range must carry a one-line "why is this fuzzy" note directly attached (e.g. "no combat-system profile for this system"), not left to be inferred from the visual treatment alone, or a DM will read it as the tool being unsure of itself rather than being honest.

**Catalog score chips are intrinsic, not party-relative — resolving an open question from round 3.** A West Marches DM reviewer worried that a precomputed-at-ingest score chip on each catalog row might carry a hidden, stale assumption about party shape. Resolution: the catalog's per-row score chip (`computeActionEconomyScore`'s output, plus the impact fingerprint) is a property of the monster alone — it is never computed against any party and carries no such assumption to hide. Party-relative numbers (`expectedScore`, snowball delta) only ever appear once something is actually in the working roster, at which point the attendance-staleness line already states what roster they're scoped to. No new UI surface needed to resolve this — the concern dissolves once the two kinds of number are kept visibly separate, which the design already does.

**Ingestion is a separate, prior screen — not part of the builder's moment-to-moment flow.** Pasting/uploading a stat block or character sheet, reviewing the extracted raw fields, and accepting/discarding the entry happens on its own screen (`bestiary-store.mjs`/`party-roster-store.mjs`'s accept/discard lifecycle), before an entry ever appears in the builder's catalog. Per round-3 refinement (raised twice, independently, as the thing that matters more than any scoring UI polish): the review screen must flag low-confidence extracted fields **inline, per field**, not present a binary "extraction succeeded" state — a DM needs to know which fields to eyeball and which to trust without re-deriving that judgment from scratch every time they add a monster mid-campaign.

## 2. Where LLM calls actually happen (confirmed, worth stating explicitly since it shapes what needs a loading/latency treatment in the UI)

Exactly two places, both outside the moment-to-moment builder screen:
- **Ingestion** (`proposeBestiaryEntryFromText/FromPdf`, `proposePartyMemberFromText/FromPdf`) — a one-time-per-entry call on the ingestion screen, extraction only, never a score.
- **The optional theme box** (`proposeThematicTags`) — only if a DM types into it; left blank, never called.

Everything else described in §1 — the difficulty-rail suggestion, the live-updating score band, both disclosures, the catalog filters, the resync button — is deterministic, local, and instant. This matters for the task plan: only the ingestion screen and the optional theme box need any "still working" / latency affordance (this project's existing `withSlowNotice` pattern from `graph-view.js`); the rest of the builder should never show a loading state at all.

## 3. Explicitly out of scope / deferred

- **Roster pool pruning/archiving** — a West Marches DM flagged that a long-running character pool will accumulate one-and-done adventurers over time and should eventually be prunable. Explicitly named as a future concern, not this phase's problem.
- **A unified multi-system catalog browsing experience** — the second UX designer's decisive call, unchallenged in review: portability means the tool fully works for whichever single system a DM is actually running, not that one screen elegantly blends monsters from different systems as routine, everyday work. The System selector's "All systems" state exists as a working escape hatch, not a design investment.
- **`checkStaleness`-style proactive nudging** for the encounter builder (distinct from Phase 16/17's Session Planner concept of the same name) — not raised in this round, not designed here.
- Anything to do with maps, terrain, or positioning — no signal for it emerged in this round; if it surfaces later, it gets its own design round, not a retrofit onto this one.

## 4. Process note

Research (Kobold Fight Club/KF+C, D&D Beyond, Foundry's PF2e/Draw Steel encounter modules, HeroMuster's cross-system fallback, the "catalog + cart" / deck-builder UX pattern family) grounded both UX proposals in cited prior art rather than invented patterns. Four DM personas (tactical/precision, narrative-light-combat, minimal-prep/Sly-Flourish, West-Marches/sandbox) reacted twice — first open-ended with no design shown, then against the two UX designers' concrete proposal — genuinely refining the design across the exchange rather than just validating a single draft. Both UX designers grounded their proposals directly in the real shipped Phase 18 code (`encounter-heuristic.mjs`, `snowball-delta.mjs`, `effect-impact.mjs`, `bestiary-store.mjs`, `thematic-filter.mjs`), not a speculative API shape. The shape in §1 was then walked through in plain language with the project owner and confirmed before task-planning.
