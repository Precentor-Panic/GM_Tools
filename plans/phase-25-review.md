# GM_Tools — Phase 25 Design Record: The Information-Cockpit Table-Read View

**Status:** design finalized — 5-persona review round complete (4 DM personas + 1 UX/dashboard-expert persona) and directly adjudicated by the project owner (§5). Ready for task-planning. Per `plans/phase-21-review.md` §8/§12's explicit instruction that this get its own dedicated design/research round — not scoped as an afterthought inside the construction UI — sequenced after Phase 23 shipped (it has: `session-planner-view.js`'s chain display, add/remove-node, Develop-node/-scene, scene-local rollback, equal-weight Add Event/Add Encounter, mid-session quick-gen "+", all independently verified). Grounded in real research (§1) and the actual, already-shipped data a scene exposes today (§2) — not a speculative UI, per §12's own warning against researching a UI that doesn't exist yet.

---

## 0. The problem, restated precisely

Phase 17 built the original Session Planner cards around an "aggressively simplified" target. The project owner's own direct, much earlier feedback on that shipped result: *"the cards on that session plan tab really don't do a ton in terms of surfacing information."* Phase 21 §8 corrected the target explicitly: not further simplification, an **information cockpit** — dense, complex information organized for fast at-a-glance access, the way a pilot's cockpit surfaces a lot of real information at a glance rather than hiding it for the sake of looking clean.

This phase is scoped narrowly: design (and, after persona review, build) the **at-table live-read surface** — what a DM glances at *during play*, under real time pressure (a few seconds, not careful reading), on a laptop or a tablet/phone propped at the table. It is explicitly NOT a redesign of Phase 23's construction UI, which stays as the prep-time editing surface (chain display, add/remove-node, develop-scene, rollback). Those are different jobs done at different times with different pressure — conflating them is exactly the mistake this design record exists to avoid repeating.

## 1. Research grounding (full report available on request; summarized here)

Real prior art from domains built specifically for fast-glance, high-stakes information density was researched directly (aviation/HUD design, trading terminals, NOC/monitoring dashboards, patient monitors, and existing GM-screen/VTT tools), not assumed. Five load-bearing findings, in priority order:

1. **Fixed-zone layout, identical across every scene and every breakpoint** (aviation "basic six," Bloomberg's non-reflowing panels, NN/g's spatial-memory research). Spatial memory — knowing *where* to look without reading a label first — is what makes a 2-3 second glance work at all, and it only forms when position is stable. NN/g's guidance is explicit: **scale a dense layout down for smaller screens, don't reflow it** — adaptive layouts that rearrange content "have generally not worked well" because they destroy the very muscle memory that makes fast-glance possible.
2. **Redundant status coding — color + icon + fixed meaning, never color alone** (NOC dashboards, patient monitors). A second finding from NOC research is directly relevant to an app that already has flag badges: **don't let a merely-incomplete/undeveloped scene use the same visual urgency as an active in-play problem** — sustained "alarm" treatment on a low-stakes state causes exactly the desensitization this app should avoid, given it already ships `flag-badge--content`/`flag-badge--structural` badges today.
3. **In-place progressive disclosure via a persistent, visible trigger — never a route/modal, never hover-only.** A concrete, documented failure case (a competing VTT's GM interface, independently reviewed) found that scattering one piece of needed information across multiple modal panels — "multiple places to accomplish something," can't roll dice while a sheet is open — was rated "somewhere between extremely inconvenient and downright impossible" mid-session. The fix implied is direct: every dense card shows a compact summary permanently, deeper detail expands inline (accordion-style), and touch devices need a real tap target since hover doesn't exist there.
4. **Tabular/aligned typography, oversized key numerals for the handful of numbers that matter** (Bloomberg column alignment, patient-monitor "readable across the room" sizing). Spend legibility budget on the 3-5 numbers that actually matter per card (HP/AC on a stat block, not every field), not evenly.
5. **Scale, don't reflow; if a phone forces single-column, pin a persistent status strip** — the closest analogue to a primary flight display: the 3-5 most critical indicators stay visible regardless of scroll position, so the core glance never requires hunting.

An existing GM-screen precedent (Foundry VTT's own "GM Screen" module, and third-party tools like Overseer Studio) independently converged on the same underlying answer this project is reaching for: **do the work of finding information at prep time, make live retrieval pure lookup.** That is already this whole redesign's architecture (Phase 22's engine + Phase 23's construction UI build the dense record; this phase is purely the read-optimized presentation of what already exists) — the research confirms the shape of the plan, it doesn't change it.

## 2. What data already exists to draw on (grounded directly in shipped code, not assumed)

**Currently surfaced** (Phase 17/23's `renderLocationCard`, `review-ui/public/session-planner-view.js`): entity name, type, digest (`{name, roleTag, hook}` — a hard-capped ≤15-word single fact, per `session-planner/digest.mjs`'s "empty-render rule": omitted entirely, never padded, when there's nothing real to show), `contentFlag`/`structuralFlag` badges, hop-distance/role (anchor/satellite/added), per-location notes.

**Committed, real, and NOT currently surfaced anywhere in the UI** (`foundry_worldFabric/scripts/data/graph-service.mjs`'s `upsertEntity` field list): `description` (full text), `summary`, `imageUrl` (a portrait/reference image, if set), `tags`, `status`, `role`, `importance`, `playerKnown`. This is real, already-committed information sitting unused — a cockpit view surfacing even a subset of this (portrait thumbnail, full description on expand) is pure retrieval of existing data, zero new engine work.

**Scene-level data already available via existing routes, not currently unified in one glanceable place:** pending notes/events (`session-notes.mjs`), saved encounters (`combat-planning/saved-encounter.mjs`) — and saved encounters carry a **full snapshotted bestiary stat block per creature** (name, HP, AC, attacks, traits — confirmed directly in `bestiary/*.json`'s real shape), taken at save time specifically so it doesn't drift if the source bestiary entry changes later. This is exactly the kind of "readable across the room" combat-reference data patient-monitor research calls out — currently it only exists behind Encounter Builder's own separate view, not glanceable from the scene a DM is actually running.

**Explicitly NOT available today, flagged as an open question, not assumed into scope:** `brief.mjs`'s own `checkStaleness(world, scene, currentLocationEntityId)` function already exists and is tested (`test/session-planner/brief.test.mjs`) but is wired into no route and no UI — there is currently no mechanism anywhere that records "where the party actually is right now" for it to compare against. Building that tracking mechanism is new scope this design record does NOT propose taking on; §7 below treats it as optional/future, not required for this phase.

## 3. Proposed shape: a single-scene "Table Mode," not a chain view

The construction UI (Phase 23) is built around the whole ordered **chain** — appropriate for prep, where a DM plans several scenes ahead. Live play does not work that way: a DM is running **one scene at a time**, and cramming an entire multi-scene chain into one glanceable cockpit view directly contradicts finding #1 (fixed zones only work if there's a small, stable set of them — a chain of arbitrary length can't have a fixed layout).

**Proposal:** a **Table Mode** toggle on the currently-open scene (sibling to, not replacing, the existing Prep/construction view) that renders *only the current scene* in a fixed-zone cockpit layout, plus an in-place **navigation zone** (§3a) that never requires leaving Table Mode to reach another scene.

### Fixed zones (identical positions across every scene, scaled not reflowed for tablet/phone)

- **Top strip (always visible, never scrolls away)** — location name, on-the-path badge, prep-readiness indicator using the existing flag vocabulary but with the NOC-research redundant-coding fix applied (icon shape *and* color *and* label). **Adjudicated fix, not optional**: the UX persona review found this isn't a future-proofing exercise, it's a live bug — `.flag-badge--structural` already reuses the same `--reject` error-color token as genuine error states, and `.flag-badge--content` already shares its amber token with the unrelated "nothing established at all" empty state (`.location-card-digest--empty`). Task-planning must include a real state → icon → CSS-variable → trigger-condition table (at minimum: not-developed, thin-connections, empty/no-digest) using tokens distinct from `--reject`/error, not just a design intention.
- **Main zone — member roster**, one compact row per scene member (anchor + satellites + arbitrarily-added), each row permanently showing name + roleTag + digest hook (the existing 15-word fact) with a persistent (not hover-only) expand affordance. **Adjudicated: expand is nested, not flat** — expanding a member row can itself reveal a participating node's full detail, and an expanded encounter's roster can each expand to that creature's full stat block. Per direct project-owner guidance: prioritize fast, unrestricted access to depth over pre-emptively capping how much can be open at once — "start small," ship the simple unbounded version, and let real hands-on use (not a pre-built policy) surface whether a cap or accordion is actually needed. Do not build an accordion/cap mechanism speculatively.
- **Side/secondary zone — notes &amp; encounters**, unified list of this scene's pending notes and saved encounters together (equal-weight, per Phase 21 §6's standing rule — interleaved, not two separately-sized sections). Each saved encounter shows its roster as compact stat-block rows (name, HP, AC — read-only, tabular-aligned) with the same nested-expand-inline pattern for full attacks/traits. **Explicitly tabled, not in scope for this phase** (see §4): any per-creature "what does this thing do" combat-relevant hook beyond name/HP/AC, and any HP/initiative tracking of any kind.
- **`playerKnown` gating** — the UX persona flagged that this spoiler-risk field was folded into the same casual tap-to-expand tier as flavor fields like `tags`. Adjudicated: give it a harder, more deliberate gate than a plain expand (e.g. a separate confirm-to-reveal step), not the same one-tap disclosure as everything else in a member's expanded detail.
- **Bottom strip — actions**, equal-weight per Phase 21 §6: Add Event, Add Encounter (round-trips to Encounter Builder exactly as Phase 23 already built), quick-gen "+" (Phase 22's already-shipped fast single-call primitive).

### 3a. Navigation — adjudicated design, replaces the original single "Advance" button

Three of four DM personas independently flagged "Advance to next linked scene" as an insufficient navigation gap (revisiting a non-adjacent or previous-session location is a real live-play scenario), but the project owner explicitly rejected routing out to the Scenes tab to solve it — the whole point of Table Mode is not needing to "exit" the one-location-hop experience. Adjudicated shape, a dedicated navigation zone (position: directly adjacent to the top strip, always visible, not behind a toggle):

- An **adjacent-scenes strip** — mirrors the existing "on the path" chain-neighbor concept already used in the construction UI, surfaced directly (not one click away) so moving to the scene immediately before/after the current one in the chain is a single tap, no picker, no leaving Table Mode.
- A **search bar** sitting directly above that strip, filtering down to any scene in the world (same underlying data Phase 24's Scenes tab already queries) — the search-driven jump the personas asked for, but reachable without navigating away.
- The **full scene list stays present but collapsed by default** beneath the adjacent-scenes strip — available for a manual scroll-and-browse fallback without ever being the primary or required path.

This one navigation zone replaces the original design's single "Advance" button entirely — it is the answer to open question #2 from the original draft, not an addition alongside it.

### Responsive behavior

Laptop: all zones visible at once, proportions as above. Tablet: same zones, scaled down, same relative proportions (per finding #5 — no reflow, no reordering). Phone, if a true single column becomes unavoidable: the top strip stays pinned/sticky regardless of scroll position (the "primary flight display" analogue) while the roster/notes/encounters zones stack vertically beneath it in the same top-to-bottom priority order they hold on larger screens.

## 4. Explicitly out of scope for this phase

- Any change to Phase 23's construction/prep UI — Table Mode is additive, a new rendering of already-existing scene data, not a replacement.
- Any new engine/store work beyond what §3/§3a call out. Every zone is populated from routes and data shapes that already exist and are already tested (`brief`, `session-notes`, `saved-encounter`, `scene-linkage`). If task-planning surfaces a genuine additional gap, that's a small addendum (matching this project's established Phase 18/22 addendum precedent), not a new engine phase.
- "Current party position" staleness tracking (§2's flagged gap) — `checkStaleness` exists and is tested but has no data source to compare against yet; wiring one up is a separate, future decision, not required for Table Mode to ship.
- **HP/initiative tracking of any kind — adjudicated, hard no, not deferred-maybe.** Foundry is where players have live read/write access during the session and must stay the single source of truth for player state; this cockpit view must never become a second, driftable copy of it. A future "pull HP from Foundry into the encounter builder" hook is a real, wanted idea, but belongs to a future Encounter Builder revisit, not this phase — see the project memory captured alongside this design record for the fuller idea (character-sheet-aware intake, likely LLM-assisted parsing + a verify step to identify "this is a PC sheet," since a hardcoded D&D 5e sheet parser would be the easy but narrow answer).
- **Per-creature "what does this thing do" combat-relevant hooks (tactical DM's ask) — tabled, not this phase.** Belongs with a future Encounter Builder revisit alongside the HP-pull idea above and the "combat theme" LLM filter idea (giving the theme-filtering call access to raw creature parameters so it can target a specific requested mechanic — "sticky," grapple-heavy, control-heavy — not just an overall difficulty score). None of this touches Table Mode's read surface.
- The "currently-active scene visually distinguished from merely-undeveloped ones" idea (narrative DM) and an "unresolved encounter" urgency marker (tactical DM) — both real, both explicitly agreed by their own proposers to be fine deferred past v1, no data-model support exists for either today.
- Player-facing display. This is a GM-only surface, same as everything else in this project.
- GM_MapGen/battle-map integration — still its own separately-tabled track, unaffected by this phase.

## 5. Adjudication (project owner, direct — not averaged from persona feedback)

- **Navigation**: resolved via §3a's adjacent-scenes-strip + search-bar + collapsed-full-list design, not the original single "Advance" button and not a route-out to the Scenes tab.
- **HP/initiative tracking**: hard no for this phase, tabled to a future Encounter Builder revisit (see §4).
- **Combat-relevant per-creature hooks**: tabled to the same future Encounter Builder revisit (see §4).
- **Expand/collapse**: nested (scene → member/encounter → full detail) and deliberately unbounded/uncapped for v1 — "start small," prioritize fast access to depth, let real usage (not a pre-built policy) reveal whether capping is actually needed. This directly overrides the UX persona's recommendation to pre-specify an accordion/cap policy before building — a deliberate choice, not an oversight.
- **The two UX-persona factual corrections** (flag-badge color-token reuse already reading as an error state; `playerKnown` needing a harder gate than a plain expand): adopted as real bugs/gaps to fix, independent of the rest of the adjudication.
- Everything else flagged as "fine to defer" by its own proposing persona (active-scene distinction, unresolved-encounter marker) stays deferred, not built this phase.
